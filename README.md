# Go HTTP Middleware: Redis, Rate Limiting и мониторинг

Практический набор готовых HTTP middleware для Go-приложений, который помогает решать типовые задачи при создании API: ограничивать частоту запросов, защищать операции от параллельного выполнения, работать с сессиями и очередями, атомарно изменять состояние и контролировать работу приложения через метрики.

Проект можно использовать как **готовые компоненты для своего Go-сервиса**, как основу для собственного middleware или как практический пример архитектуры HTTP-сервиса с Redis, OpenTelemetry и Prometheus.

## Что вы получите

Изучив или подключив этот проект, вы сможете:

* добавить rate limiting в HTTP API;
* реализовать распределённое ограничение запросов через Redis;
* защищать критические операции распределённой блокировкой;
* организовать обработку задач через Redis-очереди;
* хранить и продлевать TTL пользовательских сессий;
* выполнять атомарные изменения состояния по принципу compare-and-set;
* считать посещения страниц и другие события;
* добавить структурированное логирование HTTP-запросов;
* собирать метрики работы middleware;
* наблюдать за приложением через Prometheus;
* обрабатывать panic и возвращать клиенту единый JSON-ответ;
* увидеть, как выстраивать цепочку middleware в Go.

Таким образом, репозиторий полезен не только для изучения кода: отдельные middleware можно адаптировать и использовать как строительные блоки собственного HTTP-сервиса.

## Какие задачи решает проект

### 1. Ограничение частоты запросов

Пакет `ratelimit` позволяет ограничивать количество запросов от клиента.

Redis хранит счётчик запросов и TTL, а Lua-скрипт выполняет необходимые операции атомарно.

Если лимит превышен, middleware возвращает:

```text
429 Too Many Requests
```

Пример:

```go
mux.Handle(
    "/api",
    ratelimit.RateLimit(http.HandlerFunc(MyHandler)),
)
```

Это можно использовать для защиты API от чрезмерного количества запросов и контроля нагрузки.

---

## 2. Rate limiting со скользящим окном

Пакет `slidingwindow` реализует ограничение запросов с использованием скользящего окна.

В Redis хранятся временные метки запросов. Старые записи удаляются из окна, после чего определяется, разрешён ли новый запрос.

```go
mux.Handle(
    "/api",
    slidingwindow.SlidingWindow(
        5,
        1000,
    )(http.HandlerFunc(MyHandler)),
)
```

Такой подход позволяет использовать более точную модель ограничения запросов по сравнению с простым фиксированным временным окном.

---

## 3. Распределённые блокировки

Пакет `distributedlock` позволяет не допускать одновременного выполнения критической операции несколькими запросами или экземплярами приложения.

Например, это может быть полезно при обработке:

* заказов;
* платежей;
* операций с одним ресурсом;
* задач, которые нельзя выполнять параллельно.

```go
mux.Handle(
    "/order",
    distributedlock.RedisLockMiddleware(
        "lock:order:123",
        5000,
    )(http.HandlerFunc(OrderHandler)),
)
```

Redis используется как общее хранилище состояния блокировки.

---

## 4. Подсчёт посещений

Пакет `pagecounter` позволяет хранить счётчик событий в Redis.

```go
mux.Handle(
    "/page",
    pagecounter.CounterMiddleware(
        "counter:page_view",
        60,
    )(http.HandlerFunc(PageHandler)),
)
```

Текущее значение счётчика передаётся в HTTP-заголовке `X-Counter`.

Это может быть полезно для простых счётчиков посещений, событий или других операций, где требуется быстрое атомарное увеличение значения.

---

## 5. Обработка очередей задач

Пакет `queue` показывает вариант обработки задач через Redis.

Задача перемещается из исходной очереди в очередь обработки с помощью `RPOPLPUSH`.

```go
mux.Handle(
    "/task",
    queue.QueueMiddleware(
        "queue:tasks",
        "queue:processing",
    )(http.HandlerFunc(TaskHandler)),
)
```

Текущий элемент очереди передаётся через заголовок:

```text
X-Queue-Item
```

Если очередь пуста, middleware возвращает:

```text
204 No Content
```

---

## 6. Управление TTL сессии

Пакет `session` продлевает время жизни сессии в Redis при каждом запросе.

Middleware:

1. получает `session_id` из cookie;
2. проверяет существование сессии;
3. продлевает TTL;
4. возвращает `401 Unauthorized`, если сессия не найдена.

```go
mux.Handle(
    "/secure",
    session.SessionMiddleware(10)(
        http.HandlerFunc(SecureHandler),
    ),
)
```

Такой подход можно использовать для реализации механики активных пользовательских сессий.

---

## 7. Атомарное обновление состояния

Пакет `stateupdate` реализует обновление значения в Redis по принципу **compare-and-set**.

Сначала проверяется текущее значение:

```text
old
```

Если оно совпадает с ожидаемым, устанавливается новое:

```text
new
```

Если состояние уже изменилось, возвращается:

```text
409 Conflict
```

Пример:

```go
mux.Handle(
    "/update",
    stateupdate.StateUpdateMiddleware(
        "state:item123",
        "old",
        "new",
    )(http.HandlerFunc(UpdateHandler)),
)
```

Это позволяет контролировать конкурентные изменения состояния без простой схемы «прочитал → изменил → записал».

# HTTP Middleware

Проект демонстрирует цепочку middleware, через которую проходит HTTP-запрос:

```text
Client
   │
   ▼
Recovery
   │
   ▼
Logging
   │
   ▼
Metrics
   │
   ▼
Auth
   │
   ▼
RateLimit
   │
   ▼
Handler
   │
   ▼
JSON Response
```

Каждый middleware отвечает за отдельную задачу.

Это позволяет разделять ответственность и собирать необходимую функциональность в нужную цепочку.

---

# Structured Logging

Пакет `logging` предоставляет структурированное логирование HTTP-запросов с использованием `zerolog`.

В логах можно сохранять такие данные, как:

* HTTP-метод;
* путь;
* статус ответа;
* длительность запроса;
* `user_id`;
* дополнительные поля.

Это делает логи удобнее для последующего анализа и поиска проблем.

# Метрики и Prometheus

Приложение собирает метрики с помощью OpenTelemetry и предоставляет их через endpoint:

```text
/metrics
```

Например:

```bash
curl http://localhost:8080/metrics
```

Prometheus может опрашивать этот endpoint и получать статистику работы приложения.

Отслеживаются, в частности:

* успешные и неуспешные авторизации;
* разрешённые и заблокированные запросы;
* запросы sliding window;
* активные и истёкшие сессии;
* успешные и неудачные обновления состояния;
* обработка очередей;
* просмотры страниц;
* успешные и заблокированные операции distributed lock;
* перехваченные panic.

В результате разработчик получает возможность наблюдать не только за HTTP-сервисом, но и за работой отдельных middleware.

# Recovery Middleware

`Recovery` перехватывает panic в оборачиваемых HTTP handler и возвращает клиенту JSON-ответ с ошибкой `500`.

Также собираются метрики:

```text
recovery_panic_total
recovery_success_total
recovery_duration_seconds
```

Важно учитывать порядок middleware.

Если внутри самого handler используется собственный `recover`, panic не дойдёт до `Recovery` middleware и соответствующая метрика не будет увеличена.

---

# Правильный порядок middleware

Пример цепочки:

```go
Chain(
    handler,
    recovery.Recovery,
    logging.Logging,
    metrics.Metrics,
    auth.Auth,
    ratelimit.RateLimit,
)
```

Порядок имеет значение.

`Recovery` располагается сверху, чтобы перехватывать panic.

`Logging` позволяет фиксировать запросы и результаты их выполнения.

`Metrics` собирает статистику.

`Auth` проверяет авторизацию.

`RateLimit` ограничивает частоту запросов.

И только после прохождения middleware выполняется основной handler.

# Запуск проекта

Для работы проекта требуется Redis.

Самый простой вариант — запустить Redis через Docker:

```bash
docker run -p 6379:6379 redis
```

После настройки подключения к Redis можно запустить приложение:

```bash
go run main.go
```
